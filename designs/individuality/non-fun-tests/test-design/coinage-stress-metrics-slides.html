Stress testing Coinage: what we measured and why

Five flows on a local PreviewNet, from 100 to 150,000 actors

About 15 minutes. Plan: why a chain is different (2 min), the metrics and where they come from (3 min), the scenarios (2 min), five results (6 min), limits and next steps (2 min).

Starting point

A chain is not a REST API, but we can test it like one

REST API

  • Send a request
  • Get a response
  • Done: you know if it worked

Coinage transaction

  • Send it, and it waits in a pool
  • It goes into a block
  • The block becomes final
  • Only then do we know if it worked

So I took the metrics we use for REST API load tests, like JMeter's, and changed what "a response" means.

The node answering "accepted" is not the response. A node can accept a transaction and lose it later. The real response is a successful receipt in a finalized block.

The metrics

From JMeter to Coinage

JMeter / REST API testWhat we measure in CoinageWhy it matters
Assertion passedVerified receipt + correct final coin stateDid the money actually move?
Error %Transactions with no verified receiptA lost payment is the worst outcome
HTTP 503 / connection refusedPool rejections (error 1016)What a spike looks like at the door
Response time: median, 95% and 99% lineFinality p50 / p95 / p99How long people at the back wait
Throughput (requests/s)Transactions per blockHow fast a queue can drain
Thread group ramp-upBurst vs waves, and pool sizeDoes spreading the load help?
Server monitoring (PerfMon)Machine CPU and memoryDid we test the chain or our tooling?

One Coinage-only metric: readiness, when a new coin can actually be used. REST APIs have no equivalent.

I report p95 rather than the average because the average hides the people at the back of the queue. We do not report a TPS number, because a finite burst does not show a sustainable rate.

The scenarios

Five flows, each a burst of signed transactions

FlowWhat one actor doesLargest verified run
Top-upPays with an external asset, gets a voucher10,000
ClaimTransfers one coin150,000
Split-and-claimSplits a coin, then claims it100,000 actors
RecyclingLoads a coin into a recycler40,000
Merchant fan-inPays one merchant20,000
Unloads (quota, offboarding)Cashes out to the external asset10,000 (preliminary)

Each flow ran at several sizes, sent all at once or in waves, on the default pool or a bigger one. Not covered: the wallet planner, chat, TrUAPI and the mobile screens.

All on one parity-large runner: 32 logical CPUs, 62.8 GiB RAM, 6 relay validators and 2 People collators, with the load generator on the same machine. Full flow, sponsored pot, cleanup backlog and instance proliferation are not run yet.

Result 1 · Correctness

150,000
claims in one burst: 150,000 verified receipts, zero errors
200,000split-and-claim receipts, all verified
20,000merchant payments, all verified
1,000,000did not run: our load generator ran out of memory
Every passing run had zero errors in its receipts and coin states. The one-million failure is a test tool limit, not a chain limit.

Result 2 · Throughput

The block, not the pool, sets the speed

Every full block held exactly 2,363 claims and stopped at the block weight limit. A bigger pool lets more claims wait; it doesn't make blocks hold more.

This is our throughput metric. Instead of requests per second, it's transactions per block. The queue drains by about 2,363 claims each block.

Result 3 · Error rate under a spike

10,000 at once on the default pool: 1 in 10 rejected

The default pool holds 9,011 (8,192 ready + 819 future). Sending in waves fixed it in every flow, and so did a bigger pool wherever we have a result.

This is our "ramp-up" finding. Same total load, different arrival pattern: a single spike fails, waves pass.

Result 4 · Response time

Response time grows in a straight line with load

Each extra 1,000 top-ups added about 22 s to finality p95 and 28 s to readiness p95.

This follows from Result 2: a fixed number per block means a queue drains at a steady rate, so wait time grows with queue length. Four passing runs only, so a strong pattern, not a model.

Result 5 · The slowest flow

Unloads: only 23 fit in a block

2,363claims per full block
23unloads per full block
  • Each unload uses 62.9 ms of the 1.5 s block budget, so 23 fit and a 24th doesn't.
  • 10,000 offboards at once took 56 minutes at p95. In waves, all 10,000 verified.
Unload cases are still preliminary: two of six offboarding profiles and four of six quota profiles have no result yet.

Server monitoring

The machine was not the limit

CPU: about 5% idle → 12% average, 21% peak during 100,000 claims. Memory 12 → 19.8 GiB, partly our load generator.

Like PerfMon in JMeter: it tells us whether we measured the chain or our own tooling. Here the chain's block limit was the bottleneck, not the hardware.

Wrap-up

What this does and doesn't show

  • Shows: what bursts Coinage completed correctly, how long people waited, and where the limit is (block weight, not hardware).
  • Doesn't show: a sustainable TPS or a capacity ceiling. These were finite bursts.
  • Next: the remaining quota and offboarding profiles, full flow, sustained load, sponsored pot, cleanup backlog and instance proliferation.
Acceptance tells us a transaction got in the door. A verified receipt tells us the money moved.
