"Accepted" only means it got in the door. We only know it worked at the end.

So I took the metrics we use for REST API load tests, like JMeter's, and changed what "a response" means: a successful receipt in a finalized block.

The node answering "accepted" is not the response. A node can accept a transaction and lose it later. The real response is a successful receipt in a finalized block.

The metrics

From JMeter to Coinage

JMeter / REST APIWhat we measure in CoinageWhy it matters
Assertion passed→Verified receipt + correct coin stateDid the money actually move?
Error %→No verified receiptA lost payment is the worst outcome
HTTP 503 / refused→Pool rejections (error 1016)What a spike looks like at the door
Median, 95% and 99% line→Finality p50 / p95 / p99How long people at the back wait
Throughput (requests/s)→Transactions per blockHow fast a queue can drain
Thread group ramp-up→At once vs in waves; pool sizeDoes spreading the load help?
Server monitoring (PerfMon)→Machine CPU and memoryDid we test the chain or our tooling?

One Coinage-only metric: readiness, when a new coin can actually be used. REST APIs have no equivalent.

I report p95 rather than the average because the average hides the people at the back of the queue. We do not report a TPS number, because a finite burst does not show a sustainable rate.

Result 2 · Throughput

The block, not the pool, sets the speed

2,363
claims in every full block

Every full block stopped at the block weight limit.

A bigger pool lets more claims wait. It doesn't make blocks hold more.

This is our throughput metric. Instead of requests per second, it's transactions per block. The queue drains by about 2,363 claims each block.

All six free-quota profiles now have results; offboarding is still preliminary (10,000 on a bigger pool has no result, and 20,000 has incomplete receipt evidence). Every full unload block in every case held 23.

Finality p95 per stage. Each person follows one fixed plan: top-up → unload into a payment coin → claim → recycle → offboard. Not the wallet planner.

Smoke and 100 people also passed every stage. 10,000 at once was a test-tool failure: our sender lost its connection, so no load reached the chain; a retry is running. The two unload stages take most of the time because each block fits only 23 unloads. Per-block numbers for the other stages are what we saw, not capacity.

Server monitoring

The machine was not the limit

21%
peak CPU during 100,000 claims

About 5% idle → 12% average across 32 CPUs.

Memory 12 → 19.8 GiB, partly our load generator.

Like PerfMon in JMeter: it tells us whether we measured the chain or our own tooling. Here the chain's block limit was the bottleneck, not the hardware.

Wrap-up

What this does and doesn't show

Shows

Which bursts Coinage completed correctly, how long people waited, and where the limit is: block weight, not hardware.

Doesn't show

A sustainable TPS or a capacity ceiling. These were finite bursts.
